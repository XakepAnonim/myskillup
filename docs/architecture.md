# Архитектура проекта "Менеджер задач"

## 1. Назначение документа

Документ описывает архитектуру первой версии консольного приложения "Менеджер задач", обязанности модулей, контракты операций и план реализации.

Основание для проектирования: [requirements.md](requirements.md).

Последующее уточнение по урокам 408/409 добавляет длину названия 1–80 и поле priority 1/2/3. Ниже обновлены только связанные проектные контракты, модель и будущие проверки. Это план приложения, а не результат выполнения его TC; ранее опубликованные версии документов 402/403 не переписываются.

**Статус:** проектирование. Описанные модули и операции пока не реализованы.

## 2. Цель и границы первой версии

Цель приложения состоит в предоставлении пользователю простого инструмента для учёта личных задач.

Первая версия должна поддерживать:

- FR-01. Создание задачи.
- FR-02. Просмотр списка задач.
- FR-03. Отметку задачи как выполненной.
- FR-04. Сохранение и восстановление задач между запусками.

Редактирование, удаление, поиск, авторизация, синхронизация и графический интерфейс не входят в первую версию.

## 3. Структура проекта

Планируемая структура:

```text
python/
└── 02_task_manager/
    ├── main.py
    ├── cli.py
    ├── tasks.py
    └── storage.py
```

### Ответственность модулей

| Модуль | Ответственность |
|---|---|
| main.py | Точка входа, создание компонентов, управление выполнением команд и координация сохранения |
| cli.py | Получение команд пользователя, отображение задач, сообщений и ошибок |
| tasks.py | Создание, просмотр и завершение задач, проверка названий и идентификаторов |
| storage.py | Чтение и сохранение задач в локальном файле |

Модуль `tasks.py` также определяет модель задачи, содержащую идентификатор, название, статус и priority.

### Разделение ответственности

- Интерфейс не выполняет бизнес-операции самостоятельно.
- Логика задач не обращается непосредственно к файлам.
- Хранение данных не обрабатывает пользовательские команды.
- `main.py` связывает остальные модули и управляет последовательностью их вызовов.

### Карточка cli.py

Ответственность состоит в получении команд и строк пользователя, отображении списка, результатов и сообщений.

Не отвечает за создание и завершение задач, назначение ID, чтение и запись файла. В сценарии создания получает также текст приоритета.

Входом служат запросы `main.py` на ввод или вывод, а также строки пользователя. Выходом служат выбранная команда и введённые строки; сообщения выводятся пользователю. Коллекция задач не изменяется.

Ошибки ввода отображаются по решению `main.py`; после неизвестной команды или нечислового ID показывается меню согласно NFR-01. Ошибка логики или хранения не превращается в сообщение об успехе.

Зависимости ограничены консольным вводом и выводом. `cli.py` не вызывает `tasks.py` и `storage.py`; его функции вызывает координатор `main.py`.

### Карточка tasks.py

Ответственность состоит в проверке длины нормализованного названия 1–80 и priority 1/2/3, создании задачи с новым ID, получении списка и завершении задачи по ID.

Не отвечает за `input()`, `print()`, разбор команд и файловое хранение.

Входом служат текущий список корректных задач, название и целочисленный priority при создании либо положительный целочисленный ID при завершении. Выходом служат созданная или завершённая задача либо коллекция для просмотра. При создании изменяется список, при завершении только статус найденной задачи; просмотр состояния не меняет.

Пустое или слишком длинное название либо priority вне 1/2/3 приводят к ожидаемой `ValueError`, неизвестный ID приводит к ожидаемой `LookupError`. При этих ошибках весь список остаётся неизменным. Повторное завершение допустимо без создания дубликата.

Модуль использует принятую в этом проекте модель задачи и не зависит от интерфейса или хранения. Ожидаемые ошибки обрабатывает `main.py`.

### Карточка storage.py

Ответственность состоит в загрузке и проверке JSON в UTF-8, а также записи списка задач в этот формат.

Не отвечает за пользовательские команды, назначение ID и изменение статуса задачи.

Входом служат путь к файлу и список корректных задач для сохранения. Выходом загрузки служит полностью проверенный список, выходом сохранения является успешное завершение либо ожидаемая ошибка. Загрузка не изменяет файл; сохранение записывает список в файл.

Отсутствующий файл при первом запуске даёт пустой список. Ошибка чтения, повреждённый JSON или нарушение схемы передаются в `main.py`; файл автоматически не перезаписывается. Ошибка записи также передаётся в `main.py`, который сообщает, что изменение не сохранено.

Зависимости ограничены файловой системой, форматом JSON и схемой задачи. Модуль не вызывает `cli.py` и не меняет текущую коллекцию задач при сохранении. Атомарная запись пока отдельно не спроектирована.

### Роль точки входа main.py

`main.py` хранит текущий список в памяти и передаёт его операциям `tasks.py`. При запуске получает список из `storage.load_tasks`, затем запрашивает команды через `cli.py`. До вызова `complete_task` преобразует строковый ID в положительное целое число. Неизвестную команду и ошибку преобразования обрабатывает сообщением и возвратом к меню без изменения задач.

При создании `main.py` сначала проверяет длину нормализованного названия 1–80; отказ исключает запрос приоритета. Ввод приоритета после strip() проверяется в `main.py` явными равенствами "1" или "2" или "3" через or; только затем выполняется int() и вызов логики с целочисленным priority. Проверки длины названия и диапазона priority повторно защищаются контрактом `tasks.create_task`, независимо от интерфейса.

После успешного изменения `main.py` вызывает сохранение. Только успешная запись допускает сообщение "Сохранено". При ошибке записи изменение остаётся в памяти, а пользователь получает предупреждение "Изменение не сохранено". При ошибке первоначальной загрузки `main.py` показывает сообщение через `cli.py` и завершает запуск без вызова сохранения.

## 4. Схема взаимодействия

```text
Пользователь <-> cli.py
main.py -> cli.py       (получить команду / показать результат)
main.py -> tasks.py     (выполнить операцию над текущим списком)
main.py -> storage.py   (загрузить / сохранить список)
```

Стрелка `->` обозначает вызов координатором функции модуля. Результат или ожидаемая ошибка возвращаются в `main.py` по тому же взаимодействию; схема не задаёт обязательный Python-import. Стрелка `<->` обозначает пользовательский ввод и отображение сообщений. Наследования и сетевых запросов на схеме нет.

При запуске `main.py` загружает проверенный список через `storage.py`, хранит его в памяти и передаёт операциям `tasks.py`. Ошибка загрузки приводит к сообщению и завершению запуска без сохранения.

При выполнении команды `main.py` передаёт пользовательский запрос в `tasks.py`. После успешного изменения задач вызывает `storage.py` для сохранения.

`cli.py` отображает результат операции или сообщение об ошибке.

Таким образом, точкой координации интерфейса, логики и хранения является `main.py`.

## 5. Модель данных

Одна задача содержит следующие поля.

| Поле | Тип | Назначение |
|---|---|---|
| id | int | Уникальный идентификатор задачи |
| title | str | Название длиной 1–80 после strip() |
| status | str | Статус выполнения |
| priority | int | 1 "низкий", 2 "обычный", 3 "высокий" |

Допустимые статусы:

- "Не выполнена".
- "Выполнена".

При создании задачи назначается статус "Не выполнена".

Идентификаторы новых задач не должны совпадать с идентификаторами существующих задач. После сохранения и повторной загрузки идентификаторы сохраняются.

### Инварианты и формат хранения

- ID является положительным целым числом. В пустом списке назначается 1, иначе максимальный существующий ID плюс 1. Перестановка списка не изменяет ID.
- `title` имеет тип `str`, нормализуется через strip() и имеет длину 1–80 включительно. Внутренние пробелы сохраняются, одинаковые названия у разных задач разрешены.
- `priority` имеет тип `int` и равен только 1, 2 или 3; он не изменяет статус и не задаёт срок или сортировку.
- `status` имеет тип `str` и принимает только "Не выполнена" или "Выполнена".
- Повторное завершение сохраняет статус "Выполнена" и количество задач. При неизвестном ID весь список остаётся неизменным.

JSON содержит список объектов с обязательными полями `id`, `title`, `status`, `priority`, например:

```json
[{"id": 1, "title": "Подготовить отчёт", "status": "Не выполнена", "priority": 2}]
```

При загрузке проверяются тип списка, наличие и типы обязательных полей, положительность и уникальность ID, длина названия 1–80 после strip(), допустимый в этом проекте статус и целочисленный priority из 1/2/3. Логические значения JSON не принимаются вместо целочисленных ID или priority. Загруженное название нормализуется через strip(). Вся загрузка отклоняется, если хотя бы одна задача нарушает схему; частично принятый список не возвращается. Исходный файл при этом не перезаписывается.

## 6. Контракты операций

### 6.1. create_task

Модуль: `tasks.py`.

Вход: текущий изменяемый список корректных задач, название задачи типа `str` и priority типа `int` из 1/2/3. Список и параметры передаются из `main.py`; текст приоритета проверен на точные формы до int().

Результат: созданная задача с нормализованным через strip() названием длиной 1–80, заданным priority, уникальным положительным ID и начальным статусом "Не выполнена". ID равен 1 для пустого списка либо максимальному существующему ID плюс 1; совпадающее название разрешено.

Изменения: новая задача добавляется в текущий набор задач.

Ошибки: при длине названия после strip() вне 1–80 или priority не из целых 1/2/3 ожидается `ValueError`; новая задача не создаётся, весь список остаётся неизменным.

Проверки длины нормализованного названия и допустимого priority выполняются в `tasks.py`, поскольку относятся к правилам создания задачи.

Связь: FR-01, AC-01, AC-02, AC-03, AC-04, AC-13, AC-14.

### 6.2. list_tasks

Модуль: `tasks.py`.

Вход: текущий список корректных задач из `main.py`. Дополнительных параметров нет.

Результат: коллекция текущих задач с идентификаторами, названиями и статусами.

Изменения: отсутствуют.

Ошибки: отсутствие задач не считается ошибкой.

При пустой коллекции `cli.py` отображает сообщение "Список задач пуст".

Связь: FR-02, AC-05.

### 6.3. complete_task

Модуль: `tasks.py`.

Вход: текущий изменяемый список корректных задач и положительный идентификатор задачи типа `int`. Преобразование строки пользователя выполнено в `main.py` до вызова.

Результат: задача со статусом "Выполнена".

Изменения: статус выбранной задачи изменяется на "Выполнена", остальные задачи неизменны. Повторный вызов для выполненной задачи сохраняет её статус и количество задач.

Ошибки: если идентификатор не найден, ожидается `LookupError`, весь список остаётся неизменным.

Связь: FR-03, AC-06, AC-11.

### 6.4. load_tasks

Модуль: `storage.py`.

Вход: путь к локальному файлу данных.

Результат: полностью проверенный список задач из локального JSON в UTF-8. Проверки схемы и инвариантов описаны в разделе 5.

Изменения: состояние задач в файле не изменяется.

Особые случаи: при первом запуске, когда файл отсутствует, возвращается пустая коллекция.

Ошибки: ожидаемые ошибки чтения, повреждённый JSON и нарушение схемы передаются в `main.py`. Координатор показывает сообщение через `cli.py` и завершает запуск без сохранения. Частично проверенный список не используется, исходный файл не заменяется пустым списком и не перезаписывается автоматически.

Связь: FR-04, AC-07, AC-08, AC-09.

### 6.5. save_tasks

Модуль: `storage.py`.

Вход: коллекция задач и путь к файлу.

Результат: подтверждение успешного завершения сохранения.

Изменения: данные задач записываются в локальный файл.

Ошибки: если запись невозможна, ожидаемая ошибка передаётся в `main.py`, а пользователь получает предупреждение "Изменение не сохранено". Изменённый список остаётся в памяти текущего запуска, сообщения об успешном сохранении нет. Защита от частичной записи и атомарное сохранение пока не спроектированы и не заявляются.

Связь: FR-04, AC-07, AC-10.

| FR-01 | main.py / точная проверка текста, tasks.py / create_task | AC-14 | TC-16 |
| FR-02 | tasks.py / list_tasks, cli.py / вывод списка | AC-05 | TC-05, TC-06 |

C-01 учитывается консольным интерфейсом и локальной координацией без сети; C-02 учитывается контрактами JSON-хранилища. Их фактическая проверка относится к последующей реализации. Все AC-01–AC-14 и NFR-01 сопоставлены с будущими TC.

### Планируемые тестовые случаи

**TC-01. Создание задачи**

Вход: название "Подготовить отчёт" и приоритет "2"; отдельный вариант с названием " Подготовить отчёт ".

Ожидаемый результат: в каждом варианте создана задача с названием "Подготовить отчёт" без внешних пробелов и priority=2.

**TC-02. Уникальность идентификаторов**

Предусловие: отдельно рассматриваются пустой список и список с максимальным ID=7.

Действие: создать задачу с допустимым priority=2, во втором случае с уже существующим названием; затем переставить задачи в списке.

Ожидаемый результат: новый ID является положительным целым числом и равен соответственно 1 или 8. Совпадающее название допускается, ID уникальны и не меняются после перестановки.

**TC-03. Начальный статус**

Действие: создать задачу с допустимым priority=2.

Ожидаемый результат: статус "Не выполнена".

**TC-04. Пустое название**

Вход: пустая строка или строка из пробелов. В интерфейсе приоритет не запрашивается; для отдельной проверки контракта логики передаётся допустимый priority=2.

Ожидаемый результат: задача не создана, отображается ошибка, список и количество задач неизменны.

**TC-05. Просмотр задач**

Предусловие: существует несколько задач.

Действие: открыть список.

Ожидаемый результат: для каждой задачи показаны идентификатор, название и статус.

**TC-06. Пустой список**

Предусловие: задач нет.

Действие: открыть список.

Ожидаемый результат: сообщение "Список задач пуст".

**TC-07. Завершение задачи**

Предусловие: существует невыполненная задача.

Действие: отметить её выполненной.

Ожидаемый результат: статус выбранной задачи "Выполнена", остальные задачи неизменны.

**TC-08. Неизвестный идентификатор**

Вход: идентификатор несуществующей задачи.

Ожидаемый результат: сообщение об ошибке, весь список не изменён, сохранение после этой ошибки не вызывается.

**TC-09. Сохранение и восстановление**

Предусловие: создана и сохранена задача с известным статусом.

Действие: закрыть приложение, запустить повторно и открыть список.

Ожидаемый результат: задача восстановлена с прежним идентификатором, названием, статусом и priority.

**TC-10. Первый запуск**

Предусловие: файл данных отсутствует.

Действие: запустить приложение и открыть список.

Ожидаемый результат: приложение запускается без ошибки и отображает пустой список.

**TC-11. Повреждённый файл и нарушение схемы**

Предусловие: существует файл, который по отдельным вариантам содержит повреждённый JSON, объект вместо списка, недостающие поля, неверные типы полей, неположительный или повторяющийся ID, длину нормализованного названия вне 1–80, неизвестный статус либо отсутствующий, неверно типизированный или выходящий за 1/2/3 priority.

Действие: начать загрузку при запуске приложения.

Ожидаемый результат: показано сообщение об ошибке, запуск завершён без сохранения. Частично проверенный список не используется, исходное содержимое файла не перезаписано автоматически.

**TC-12. Невозможность сохранения**

Предусловие: задачи корректно загружены, изменение успешно выполнено в памяти, запись в выбранный файл запрещена.

Действие: выполнить сохранение после изменения.

Ожидаемый результат: показано предупреждение "Изменение не сохранено" без сообщения об успешном сохранении. Изменение остаётся в памяти текущего запуска. Гарантия атомарности записи этим сценарием не заявляется.

**TC-13. Повторное завершение**

Предусловие: задача уже имеет статус "Выполнена".

Действие: повторно завершить её по тому же ID.

Ожидаемый результат: статус остаётся "Выполнена", число задач и остальные задачи не меняются.

**TC-14. Некорректная команда или ID**

Предусловие: приложение запущено, текущий список задач известен.

Действие: по отдельности ввести неизвестную команду "wrong" и нечисловой ID "abc" при завершении задачи.

Ожидаемый результат: в каждом варианте показано понятное сообщение и затем меню, необработанного traceback нет, список задач неизменен. Этот случай покрывает NFR-01 и AC-12.

**TC-15. Длина названия после нормализации**

Предусловие: текущий список корректен. В вариантах с допустимым названием пользователь затем вводит priority=2.

Действие: отдельно передать названия из пробелов, длиной 1, 80 и 81, а также название с внешними и внутренними пробелами.

Ожидаемый результат: пробелы дают отказ по AC-04, длины 1 и 80 принимаются, 81 даёт причину "название длиннее 80 символов" без создания задачи и успеха. Внешние пробелы обрезаны, внутренние сохранены; при ошибке названия интерфейс не запрашивает приоритет.

**TC-16. Точные формы приоритета и модель задачи**

Предусловие: название допустимо, текущий список корректен.

Действие: отдельно ввести "1", "2", "3", " 2 ", затем "0", "4", "01", "+1", "1.0", "-1", "²", пустую строку и слово. Для контракта create_task отдельно передать недопустимый целочисленный priority 0 или 4.

Ожидаемый результат: допустимые формы преобразованы только после точного сравнения и создают задачу с priority 1/2/3 и соответствующей меткой. Неверные строки отклонены до int() без необработанного исключения и успеха; неверный priority в логике даёт ожидаемую ошибку. Список при отказе неизменен, статус не зависит от приоритета.

Все TC являются планом проверки Менеджера, а не результатами выполненных тестов. Локальные сценарии отдельных упражнений 407–410 не означают прохождения этих TC.

### Три мысленных прохода по схеме

Это анализ проектируемого поведения, а не результаты запуска приложения.

1. Успешное добавление. Предполагаются пустой корректно загруженный список и доступный для записи файл. `main.py` получает через `cli.py` строку " Подготовить отчёт " и допустимый текст приоритета "2", после точной проверки преобразует его в 2 и передаёт текущий список, название и priority в `tasks.create_task`. Логика нормализует и проверяет название и priority, назначает ID=1 и статус "Не выполнена", добавляет задачу с priority=2 и возвращает её. `main.py` вызывает `storage.save_tasks`, после успешной записи просит `cli.py` показать подтверждение. Ожидается одна задача в памяти и JSON; при ошибке записи вместо подтверждения нужен исход TC-12.
2. Неизвестный ID. Предполагается корректный список без ID=999. `main.py` преобразует ввод в число и вызывает `tasks.complete_task`. Логика не находит ID и возвращает ожидаемую ошибку без изменения списка. `main.py` не вызывает сохранение, просит `cli.py` показать ошибку и меню. Ожидаются неизменные задачи и файл.
3. Ошибка чтения файла. При запуске `main.py` вызывает `storage.load_tasks`. Если чтение невозможно либо JSON или схема неверны, хранилище возвращает ожидаемую ошибку вместо списка. `main.py` через `cli.py` показывает сообщение и завершает запуск без сохранения. Ожидается отсутствие автоматической перезаписи файла и ложного сообщения об успешной загрузке.

## 9. Уточнения требований

### FR-01

Проверки длины названия 1–80 после strip() и целочисленного priority 1/2/3 закреплены за операцией `create_task` модуля `tasks.py`. Точная проверка пользовательских строк приоритета до int() относится к координации интерфейса в `main.py`.

Причина: правило создания задачи должно выполняться независимо от того, каким способом пользователь взаимодействует с приложением.

### FR-04

При отсутствии файла данных `load_tasks` возвращает пустую коллекцию.

Причина: необходимо обеспечить первый запуск приложения без ошибки согласно AC-08.

Ответственность модулей согласована с уточнёнными правилами FR-01–FR-04 в `requirements.md`. Политика повреждённого файла, ошибки записи, повторного завершения и свойства NFR-01 отражена также в AC-09–AC-12 и таблице трассировки.

### Границы отдельного прототипа 410

Однократный обработчик учебного упражнения принимает add/list/help/exit после strip().lower(). В add сначала проверяется длина названия 1–80, только затем запрашивается строгое значение приоритета 1/2/3; ошибка исключает дальнейший ввод и успех. list сообщает об отсутствии списка и сохранения, help показывает допустимые команды, exit завершает запуск. Пустая или неизвестная команда не запрашивает поля.

Этот прототип не использует проектируемые модули main.py/cli.py/tasks.py/storage.py, не выдаёт ID и не сохраняет JSON. Его сообщение "Данные приняты" подтверждает только проверки. Он заканчивается после одной команды; будущее меню и возврат к нему в NFR-01 к этому прототипу не относятся. Никакая реализация Менеджера или прохождение его TC этим разделом не заявляются.
