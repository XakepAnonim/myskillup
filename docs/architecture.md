# Архитектура проекта "Менеджер задач"

## 1. Назначение документа

Документ описывает архитектуру первой версии консольного приложения "Менеджер задач", обязанности модулей, контракты операций и план реализации.

Основание для проектирования: [requirements.md](requirements.md).

**Статус:** проектирование. Описанные модули и операции пока не реализованы.

## 2. Цель и границы первой версии

Цель приложения состоит в предоставлении пользователю простого инструмента для учёта личных задач.

Первая версия должна поддерживать:

- FR-01. Создание задачи.
- FR-02. Просмотр списка задач.
- FR-03. Отметку задачи как выполненной.
- FR-04. Сохранение и восстановление задач между запусками.

Редактирование, удаление, поиск, авторизация, синхронизация и графический интерфейс не входят в первую версию.

## 3. Структура проекта

Планируемая структура:

```text
python/
└── 02_task_manager/
    ├── main.py
    ├── cli.py
    ├── tasks.py
    └── storage.py
```

### Ответственность модулей

| Модуль | Ответственность |
|---|---|
| main.py | Точка входа, создание компонентов, управление выполнением команд и координация сохранения |
| cli.py | Получение команд пользователя, отображение задач, сообщений и ошибок |
| tasks.py | Создание, просмотр и завершение задач, проверка названий и идентификаторов |
| storage.py | Чтение и сохранение задач в локальном файле |

Модуль `tasks.py` также определяет модель задачи, содержащую идентификатор, название и статус.

### Разделение ответственности

- Интерфейс не выполняет бизнес-операции самостоятельно.
- Логика задач не обращается непосредственно к файлам.
- Хранение данных не обрабатывает пользовательские команды.
- `main.py` связывает остальные модули и управляет последовательностью их вызовов.

## 4. Схема взаимодействия

```text
              Пользователь
                   |
                   v
                cli.py
                   |
                   v
                main.py
                /     \
               v       v
          tasks.py   storage.py
               \       /
                \     /
             Данные задач
```

Стрелка обозначает вызов одной части приложения другой, а не наследование или сетевой запрос.

При запуске `main.py` загружает данные через `storage.py` и передаёт их логике `tasks.py`.

При выполнении команды `main.py` передаёт пользовательский запрос в `tasks.py`. После успешного изменения задач вызывает `storage.py` для сохранения.

`cli.py` отображает результат операции или сообщение об ошибке.

Таким образом, точкой координации интерфейса, логики и хранения является `main.py`.

## 5. Модель данных

Одна задача содержит следующие поля.

| Поле | Тип | Назначение |
|---|---|---|
| id | int | Уникальный идентификатор задачи |
| title | str | Непустое название |
| status | str | Статус выполнения |

Допустимые статусы:

- "Не выполнена".
- "Выполнена".

При создании задачи назначается статус "Не выполнена".

Идентификаторы новых задач не должны совпадать с идентификаторами существующих задач. После сохранения и повторной загрузки идентификаторы сохраняются.

## 6. Контракты операций

### 6.1. create_task

Модуль: `tasks.py`.

Вход: название задачи типа `str`.

Результат: созданная задача с уникальным идентификатором и начальным статусом.

Изменения: новая задача добавляется в текущий набор задач.

Ошибки: при пустом названии или названии из одних пробелов операция отклоняется, новая задача не создаётся.

Проверка непустого названия выполняется в `tasks.py`, поскольку относится к правилам создания задачи.

Связь: FR-01, AC-01, AC-02, AC-03, AC-04.

### 6.2. list_tasks

Модуль: `tasks.py`.

Вход: дополнительных параметров нет.

Результат: коллекция текущих задач с идентификаторами, названиями и статусами.

Изменения: отсутствуют.

Ошибки: отсутствие задач не считается ошибкой.

При пустой коллекции `cli.py` отображает сообщение "Список задач пуст".

Связь: FR-02, AC-05.

### 6.3. complete_task

Модуль: `tasks.py`.

Вход: идентификатор задачи типа `int`.

Результат: задача со статусом "Выполнена".

Изменения: статус выбранной задачи изменяется на "Выполнена".

Ошибки: если идентификатор не найден, операция завершается ошибкой и не изменяет другие задачи.

Связь: FR-03, AC-06.

### 6.4. load_tasks

Модуль: `storage.py`.

Вход: путь к локальному файлу данных.

Результат: сохранённая коллекция задач.

Изменения: состояние задач в файле не изменяется.

Особые случаи: при первом запуске, когда файл отсутствует, возвращается пустая коллекция.

Ошибки: ошибки чтения и некорректные данные передаются в `main.py` для обработки. Точная политика восстановления повреждённого файла требует уточнения.

Связь: FR-04, AC-07, AC-08.

### 6.5. save_tasks

Модуль: `storage.py`.

Вход: коллекция задач и путь к файлу.

Результат: подтверждение успешного завершения сохранения.

Изменения: данные задач записываются в локальный файл.

Ошибки: если запись невозможна, ошибка передаётся в `main.py`, а пользователь получает сообщение о невозможности сохранить данные.

Связь: FR-04, AC-07.

## 7. Связь требований, операций и проверок

FR обозначает функциональное требование, AC обозначает критерий приёмки, TC обозначает тестовый случай.

| FR | Операция | AC | TC |
|---|---|---|---|
| FR-01 | create_task | AC-01 | TC-01 |
| FR-01 | create_task | AC-02 | TC-02 |
| FR-01 | create_task | AC-03 | TC-03 |
| FR-01 | create_task | AC-04 | TC-04 |
| FR-02 | list_tasks | AC-05 | TC-05, TC-06 |
| FR-03 | complete_task | AC-06 | TC-07, TC-08 |
| FR-04 | save_tasks, load_tasks | AC-07 | TC-09 |
| FR-04 | load_tasks | AC-08 | TC-10 |

### Планируемые тестовые случаи

**TC-01. Создание задачи**

Вход: название "Подготовить отчёт".

Ожидаемый результат: создана задача с указанным названием.

**TC-02. Уникальность идентификаторов**

Предусловие: существует задача с определённым идентификатором.

Действие: создать ещё одну задачу.

Ожидаемый результат: идентификаторы существующей и новой задач различаются.

**TC-03. Начальный статус**

Действие: создать задачу.

Ожидаемый результат: статус "Не выполнена".

**TC-04. Пустое название**

Вход: пустая строка или строка из пробелов.

Ожидаемый результат: задача не создана, отображается ошибка.

**TC-05. Просмотр задач**

Предусловие: существует несколько задач.

Действие: открыть список.

Ожидаемый результат: для каждой задачи показаны идентификатор, название и статус.

**TC-06. Пустой список**

Предусловие: задач нет.

Действие: открыть список.

Ожидаемый результат: сообщение "Список задач пуст".

**TC-07. Завершение задачи**

Предусловие: существует невыполненная задача.

Действие: отметить её выполненной.

Ожидаемый результат: статус "Выполнена".

**TC-08. Неизвестный идентификатор**

Вход: идентификатор несуществующей задачи.

Ожидаемый результат: сообщение об ошибке, другие задачи не изменены.

**TC-09. Сохранение и восстановление**

Предусловие: создана и сохранена задача с известным статусом.

Действие: закрыть приложение, запустить повторно и открыть список.

Ожидаемый результат: задача восстановлена с прежним идентификатором, названием и статусом.

**TC-10. Первый запуск**

Предусловие: файл данных отсутствует.

Действие: запустить приложение и открыть список.

Ожидаемый результат: приложение запускается без ошибки и отображает пустой список.

Все TC являются планом проверки, а не результатами выполненных тестов.

## 9. Уточнения требований

### FR-01

Проверка непустого названия закреплена за операцией `create_task` модуля `tasks.py`.

Причина: правило создания задачи должно выполняться независимо от того, каким способом пользователь взаимодействует с приложением.

### FR-04

При отсутствии файла данных `load_tasks` возвращает пустую коллекцию.

Причина: необходимо обеспечить первый запуск приложения без ошибки согласно AC-08.

Это уточнение ответственности модулей, а не изменение функциональных требований.

## 10. План реализации первой версии

### Этап 1. Каркас приложения и работа с задачами

- Подготовить `main.py`, `cli.py` и `tasks.py`.
- Описать модель задачи.
- Реализовать создание задачи с проверкой названия.
- Реализовать просмотр списка.
- Подготовить проверки TC-01 — TC-06.

Ожидаемый результат: создание и просмотр задач в рамках одного запуска без постоянного хранения.

### Этап 2. Завершение задач

- Реализовать `complete_task`.
- Обработать неизвестные идентификаторы.
- Подготовить TC-07 и TC-08.

### Этап 3. Постоянное хранение

- Реализовать `storage.py`.
- Подключить загрузку задач при запуске.
- Подключить сохранение после успешного изменения.
- Подготовить TC-09 и TC-10.

### Этап 4. Итоговая проверка

- Проверить все FR и AC.
- Выполнить запланированные тестовые случаи.
- Проверить создание, просмотр, завершение и восстановление задач.
- Обновить документацию по результатам реализации.
